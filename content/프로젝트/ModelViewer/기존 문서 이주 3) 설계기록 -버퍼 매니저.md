### 고민

1. 하나의 큰 버퍼를 잡으면 될 것이라고 생각했으나, 현재 코드 구조와 막상 짜면서 문제점들을 발견
    1. 디버그 용 데이터
    2. 물체마다 Stride가 다른 경우에는 Draw함수에 지정하는 Offset이 올바르지 않을까?
        1. Stride와 InputLayout 정보와 실제 버퍼에 들어있는 값들이 다르니..

디버그 용 데이터는 처음 생각한 버퍼 매니저는 Static한 물체들만 담고 있었는데, 디버그 용 데이터는 매 프레임 갱신이 되어야 한다.

→ 별도 디버그 용으로 Dynamic 버퍼와 Static 버퍼 두 개로 나누면 될까?

→ 그러나 1-b는 여전히 해결되지 않음.

- 구현하고 나니 추가된 고민

1. 공간 재사용은 어떻게 할까? 최소한의 단편화는 처리하는 게 좋지 않을까? vs 일단 빠른 렌더큐 구조 완성을 위해 확장만 한다.

→ 일단 코드 짜면서 짬날 때마다 고민한 결과 간단한 아이디어가 떠올라 처리.

### 최종 내용

- **현재 구조에서 결정한 방식**

1. 대분류로 Static / Dynamic 버퍼로 나눈다.
2. 각 버퍼는 Stride별로 큰 버퍼를 가진다.
    1. 여러 청크를 관리한다.

- **최소한의 단편화 처리**

1. 현재 버퍼는 BufferRange로 관리되므로, 제거되면 빈 공간도 BufferRange로 관리한다.
2. 새로운 데이터를 삽입할 때 빈 공간이 있으면 할당한다.
    1. 이 때 전체적으로 쭉 훑으면서 삽입했을 때 빈공간이 가장 적게 남는 BestFit 방식으로 한다.
3. 빈 공간을 담는 벡터를 추가로 둬서 해시 맵으로 관리한다.(Stride - vector<bufferRange>)
4. 삭제 할 때 빈 공간들을 탐색하면서 인접한 빈공간(앞 노드를 봤을 때 연속되면)이 있으면 BufferRange 데이터를 병합해서 크기를 확장한다.
    1. 벡터를 StartIndex 별로 정렬(오름차)해서 병합 로직이 동작할 수 있도록 한다.
