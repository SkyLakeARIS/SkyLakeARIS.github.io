이전 문서이기 때문에 내용이 정제되어 있지 않습니다. </mark>


### 고민

1. 인터넷에 정리된 SortKey 비트를 따라하는 게 편할 것 같다.
2. 하지만, 경험 및 생각해 보는 게 더 중요할 것임.
    1. 투명, 불투명 물체들은 투명이 먼저 그려지고 불투명은 나중에 그려져야 한다.
        1. 불투명은 뒤에서 앞으로 그려져야 하므로 카메라 거리 순으로 정렬되어야 한다.(멀리있는 순서로)
    2. 머티리얼도 같은 머티리얼끼리 뭉쳐있으면 좋을 것 같으므로 SortKey에 들어가야 할 것이다.
    3. 셰이더/ 텍스처도 마찬가지로 뭉쳐있으면 좋으므로 SortKey에 포함되어야 할 것으로 보임.
    4. 결국 어디에 그릴 거냐를 생각해보면, 이런 과정들이 결국 메인 렌더 타겟들에 그려진다. 따라서 이런 드로우 콜들은 렌더타겟에 종속되니까 렌더타겟이 상위 비트를 써야 한다. 아마 최상위 비트.
    5. 뷰포트도 렌더타겟에 들어 있을 수도 있다고 보여진다.
        1. 한 렌더타겟내에서 여러 영역에 렌더링 할 수 있으니까 렌더타겟보다 하위에 들어가야 하지 않을까 생각은 됨.
    6. 패스는 렌더타겟에 묶여야 할지, 렌더타겟이 패스에 묶여야 할지 잘 모르겠다.
        1. 앞으로 더 고도화 해봐야 알 것 같다.
3. 프로젝트에 맞는 설계를 하되, 생각해보면 SortKey를 변경하는 것은 별로 어려운 일은 아닌 것 같다.  
    얼마든지 상황에 맞게 미세조정이나 비트 할당이 가능할 것으로 보임.

- 막상 짜다보니 생각난 것들

막상 짜니까 각 열거형에 따라서 어떻게 Bit를 줄 것인지는 일일이 지정해 줘야 함.

→ 일단 빠른 구현을 위해 하드코딩.

→ 열거형을 애초에 BitFlag로 메기는 것은 별로겠지?

각 요소가 Key의 어느 위치에 몇 비트를 할당할지만 결정하면 되고, 각 요소 내부에서 순서 조정을 위해 특별히 값을 매길 필요는 없어 보임. 그냥 같은 값이 뭉쳐지므로.

→ 또 다시 생각해 보니 RenderTarget 같은 경우는 값으로 Pass 순서 조정이 필요함. 그래도 나머지는(몇몇개) 굳이 순서가 중요하지 않아보이는데, 조사가 필요

아이콘은 보통 배경이 투명하므로 불투명/투명 구분이 필요했다.

### 최종 내용

코드에도 적어 놓았지만, 문서로도 정리.

- **현재 구조에서 정한 렌더패킷 정렬키 값 설계**

1. 32bit를 사용한다. 값이 큰 순서로 렌더링을 한다.(내림차순 정렬)
    1. 비트 슬라이싱 설명
    2. ```
        높은 쪽 <-----------> 낮은 쪽
        ```
        
    3. 상위 비트 | 중간 비트 | 하위 비트
2. **렌더타겟**이 가장 최상위
    1. 뷰포트는 코드 작업하며 발견되었으나 우선은 간단한 하드코딩으로 넘어 갈 수 있어서 나중에 조치
    2. 패스는 아직 Shadow, default 둘 뿐이라서 렌더타켓==패스로 결정. (아직 논할 정도 아님)
3. **머티리얼**은 우선, 중간 비트를 사용한다.
    1. 아직 머티리얼 식별자가 없어서 못쓰지만, 조만간 바로 작업 들어가면 추가.
4. **셰이더**는, 머티리얼보다 높은 쪽을 사용한다.
5. **나머지 렌더 상태**는 하위 비트를 쓴다.
    1. 현재 구조에 따라서 잘 안 바뀔 것 같은 것을 높은쪽에 둔다.

사용해 보면서 정답을 찾아가는 것을 지향하며 진행.

→ 렌더타겟을 제외한 나머지는 고민하며 순서를 지정할 필요 없어보인다.

고민한 부분이 어느정도 맞지 않을까 생각됨.

- **08.01) 정렬키 값 설계 2 - 투명/불투명 추가**

투명/불투명은 현시점에서 고려 안해도 될 줄 알았는데, 빌보드 아이콘이 투명이라 고려해야 함.

1. 투명/불투명 옵션은 중간 비트로 on/off 1개 비트만 쓴다.
    1. 투명은 불투명보다 나중에 그려져야 하므로 낮은 쪽 비트를 쓴다.
    2. 중간 비트 중에서 가장 높은 비트를 사용한다.

- **08.02) 정렬키 값 설계 3 - 비트 할당 정비**

처음 생각한 것과 실제 코딩은 최상위로부터 순서대로 할당해 놓았기 때문에 재정비

1. 처음 설계 시 상위|중위|하위 비트를 나눴지만, 각각 영역이 얼마나 줄 것인지는 정하지 않았음.
    1. 상위 비트는 현재 수가 가장 적으나 넉넉하게.
        1. 5비트 할당 (31~27)
    2. 중위 비트도 수가 많지 않으나, 넉넉하게.
        1. 16비트 할당 (26~10)
        2. 머티리얼 식별자 추가해서 넣고, 텍스처도 마찬가지로 할것이므로 좀 더 넉넉하게.
            1. → 32비트에서 64비트 sortkey로 넘어가야 할 수도
    3. 하위 비트는 현재 가장 수가 많음
        1. 나머지 전체 (9~0)
        2. 다만, 하위비트는 나중에 빼도 되지 않을까 싶은 것도 있기 때문에 미래에 또 조정이 필요할지도.

- **08.02) 정렬키 값 설계 4 - Priority 정비**

1. RenderTarget (Pass) 는 순서가 중요하지만, 나머지 셰이더, 버퍼 등은 순서보다 같은 값으로 뭉치는 것이 더 중요한 듯 함.
    1. 따라서 우선순위가 필요한 값(Pass, 불투명/투명 객체)을 제외한 값은 그대로 Key값 생성에 사용

- **08.04~) 정렬키 값 설계 5 - 64bit SortKey, 텍스처 추가**

1. 같은 텍스처가 존재하면 같이 묶기 위해서 SortKey전용으로 쓸  
    16비트 SerialID 추가
    1. Hash는 너무 사이즈가 크므로 더 작은 무언가가 필요했기 때문
2. 텍스처 하나만으로 기존 32bit SortKey 절반을 차지하므로 64비트 SortKey로 확장
    1. 나중에 Material까지 Key에 추가되면 또 16비트를 사용해야 하므로 64비트가 필요함.
3. 64bit SortKey에 대한 상/중/하위 비트 할당량
    1. 상위 비트 (63-55) | 중간 비트 (54-20) | 하위 비트 (19-0)
    2. 하위 비트가 자잘하게 많아서 상위를 약간 더 줄여도 되거나, 굳이 SortKey에 포함할 이유가 없어 제거하거나. 나중에 조정.

- **08.31) 정렬키 값 설계 6 - 비트 재배치**

1. 셰이더 비트가 하위비트에 있어 중위의 상단으로 이동
    1. 기존: bTransparancy - Reserved - TexSerial
    2. 변경: bTransparancy - Shader - Reserved - TexSerial

- **09.01~06) 정렬키 값 설계 7 - DeferredShading을 위한 비트 추가**

1. GPass - MainPass(lighting)에 대한 대응을 아래와 같이 처리
2. GPass - 렌더러 내부에서 MainPass를 GPass로 처리(기존 MainPass를 활용)
3. DeferredPass - 1번의 MainPass(Lighting)에 해당하는 Pass, GPass에서 구성한 정보들을 가지고, 색상 및 Lighting 계산하여 출력
4. 추가된 RenderTarget에 따라서 아래와 같이 Priority 설정
    1. 높음 → 낮음 (큰 값이 먼저 그려짐)
    2. Shadow - Main(GPass) - Deferred(Main) - UI
    3. ```
           2       -         3             -             1                -  0        
        ```
        

- **09.07) 정렬키 값 설계 8 - sortkey 생성 및 계산 자동화**

1. 이전에 고민했던 것들을 개선하였음
    1. 컴파일 타임에 필요한 비트 수를 계산할 방법이 있는지?
    2. 비트 할당을 더 편하게 할 수 있는 방법이 있는지?
2. 현재 엔진 구조는 열거형 기반에 count방식을 따르고 있는 구조이므로 count값을 이용하여 필요한 비트 수를 계산한다.
    1. 컴파일타임에 계산할 수 있도록 constexpr함수
    2. 여러 열거타입들을 계산 할 수 있도록 템플릿으로.
    3. 다른 타입도 가능하므로 최대한 숨기기 위해 util함수로 사용하지 않음
3. 2번 함수를 사용하여 전달받은 인자 값과 타입에 대한 비트 수를 쌍으로 묶어 레이아웃으로 관리하는 테이블을 만듦
    1. 레이아웃 작성은 수작업
    2. 레이아웃에 정의되는 순서로 비트 순서이고, 기존의 상위, 중위, 하위에 대응된다.
    3. 공간을 예약하려면 reserved 영역으로 임의 비트 수만큼 레이아웃에 추가할 수는 있다
4. 3번에서 만든 테이블을 기반으로 루프 하나로 sortkey를 생성
    1. 더이상 상위, 중위, 하위의 범위를 가지지 않고 상위부터 비트를 차례대로 쪼갠다.
    2. 수작업으로 만들었던 reserve 영역은 사라진다.(3-c는 비권장, 필요할때 그때 추가하면 됨, 필요성이 없음)
