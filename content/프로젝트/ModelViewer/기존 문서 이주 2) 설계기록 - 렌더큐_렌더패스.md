### 고민

1. 한 물체가 여러 패스(셰이더)를 쓰는 경우는?
    1. 머티리얼이 재질+텍스처+셰이더+렌더 상태로 구성되는데 물체가 가지는 머티리얼 하나로 렌더패킷을 완성할 수 없음.
    2. 이런 상태별로 머티리얼을 만드는 게 나은가?
    3. 렌더 상태마다 머테리얼을 만들면 너무 많아지는거 아닌가? 메시는 하나의 머테리얼밖에 사용하지 않는데, 가정이 또 깨짐.
    4. 렌더패킷도 렌더상태를 가지도록 하고 패킷 생성 할 때, 머티리얼 값을 기반으로 하지만, 패스에 따라 렌더 상태를 바꿔주도록 할까?
        1. 해결책이 될 수 있을 것 같긴 하지만,  
            렌더패킷이 렌더상태를 들고 있으면 머티리얼 시스템인 재질+텍스처+셰이더+렌더 상태 구성의 의미가 사라지는 것 아닌가?
2. 조사 내용들은 셰이더 퍼뮤테이션에 관해서 같이 설명되는 문제로 보이고, 직접적인 관련있어 보이진 않음.
    1. 머티리얼 - 패스와 관련된 내용 - 렌더 패킷 구성
        1. 패스와 머티리얼이 가진 셰이더+렌더상태를 어떻게 분리할 수 있을까?

### 최종 내용

- **머티리얼 시스템은 결국 아래와 같은 이유로 포기(우회)**
    1. 머티리얼은 아티스트가 만드는데 해당 프로젝트는 외부 fbx 파일을 주로 사용하게 됨.
    2. 고민 문단 1번 사항들의 고민들을 해결하려면 결국 자체 정의 셰이더 혹은 셰이더 퍼뮤테이션이라고 하는 기술을 도입하는 수밖에 없어보임.
        1. 그래야 렌더 상태에 따라서 비교적 유연한 대응이 되는 것같다.(AI조사 결과)
        2. 아무리 그래도 렌더 상태가 다르다고 별도 머티리얼을 만드는 것은 메모리 사용량도 클 것 같고, 생성/삭제하는 전략 관리도 힘들 것 같다. (배보다 배꼽이 더 큼)
    3. AI 조사 결과에 따르면 고민한 내용들이 실제 업계에서도 깔끔하게 해결하거나 해결책을 찾지는 못한 것으로 보임.
        1. 일부 경우는 특수하게 처리한다던지, 셰이더 조합이 폭발하는걸 최대한 줄인다던지 하는 경우들이 전부로 보임.
- **이 프로젝트에서 선택한 설계**

1. Material을 SemiMaterial 로 강등.
    1. Material에서 셰이더(Slot포함)+렌더 상태 값을 제거한다.
2. 렌더 패킷이 렌더 상태 구조체를 들고 있는다.
    1. 렌더 패킷을 생성하는 측에서 직접 렌더 상태를 조립하여 밀어넣는다. (고민 1번 해결안)
3. 렌더 상태 구조체는 관리 편의(가독성 포함), sortKey 계산 편하게 하기 위해 구조체로 만듦.
    1. 렌더 상태 구조체에 셰이더도 포함시킨다.

- **09.03~09.07) DeferredShading 도입에 따른 RenderPass 개선**

1. MainPass와 UI가 엄연히 별도 Pass기존에는 같은 RenderTarget에 쓴다는 개념으로 사용
2. Deferred Shading 구조로 바꾸면서 아래와 같이 RenderPass개념을 RenderPacket에 도입
    1. GPass는 생각해보면 일단 렌더링과 본질적으로 크게 다를 바가 없기 때문에 MainPass를 재사용한다.
        1. 외부에 제공한다고 했을 때, 사용자는 MainPass에 그린다고 지정하면 되도록.
        2. MainPass로 지정하면 렌더러 내부적으로 GPass로 취급한다.(기존 셰이더에 MRT만 대응)
    2. DeferredPass는 라이팅 계산 및 최종 씬 병합을 위해 추가
    3. UI Pass도 같이 추가
    4. ShadowPass는 뷰포트 사이즈가 서로 달라 별도 Pass로 유지
    5. [**09.03) Deferred Rendering 설계 1 - Main을 GPass로 사용**](https://app.notion.com/p/09-03-Deferred-Rendering-1-Main-GPass-3d053c1e49dc8010ac9dd9ee6c52b691?pvs=21)
3. 재정비된 RenderPass
4. Shadow → Main(GPass) → Deferred → UI
